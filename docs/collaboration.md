# 협업 규칙

이 가이드는 총괄 세션용이다. 워커는 작업 지시서만 받으면 된다.
워커 세션은 `orchestration` 스킬의 `worker-start`로 연다. 이 가이드에 CLI 명령을 복사하지 않는다.

## 가장 중요한 원칙: 워커의 보고만 믿고 완료라고 쓰지 않는다

워커는 틀리거나, 일부만 하고 "끝났다"고 보고할 수 있다. 총괄은 아래를 **직접** 확인한 뒤에만 "끝났다"고 쓴다.

| 결과의 종류 | 총괄이 직접 하는 확인 |
|---|---|
| 커밋 | 보고한 해시가 실제로 있는지, 바뀐 파일 목록이 보고와 같은지, 지시서에 없는 파일이 섞이지 않았는지(`git show --stat`) |
| 시험 | 통과 · 실패 · 건너뜀 개수를 워커의 말이 아니라 출력 파일이나 직접 재실행으로 본다. 느리거나 환경 때문에 실패한 시험은 단독 재실행으로 원인을 가른다 |
| 파일 · 문서 | 파일이 실제로 있고 지시서의 완료 기준을 항목별로 충족하는지 읽는다. 보고와 파일 내용이 다르면 파일이 맞다 |
| 코드 사실 · 지적 | 보고한 줄 번호 · 재현 시나리오를 코드로 확인한다. 재현할 수 없는 지적은 채택하지 않는다 |
| 비밀값 · 개인 정보 | 새 파일과 diff에 키 · 토큰 · 이메일이 없는지 검사한다 |
| 완료 기준 | 지시서의 완료 기준을 하나씩 "확인함 / 확인 못 함"으로 적는다. 못 한 것은 그대로 보고한다 |

- 확인하지 못한 것은 "미확인"으로 쓴다. 확인한 척하지 않는다.
- 확인을 워커에게 다시 맡기지 않는다. 같은 워커가 자기 일을 검증하면 검증이 아니다(리뷰어는 다른 세션).
- 이 원칙은 소규모 작업에도 적용한다. 확인 방법만 가볍게 한다.

## 규칙의 우선순위

1. 전역 `~/.claude/CLAUDE.md`와 프로젝트 `CLAUDE.md`가 이 가이드보다 앞선다. 충돌하면 그쪽을 따른다.
2. 프로젝트 루트의 `ROLES.md`(역할표, "운영 값" 절)는 이 가이드의 기본값을 덮어쓴다. 단 1번을 어기는 값은 쓰지 않는다.
3. 이 가이드의 기본값은 마지막이다.
4. 이 값은 총괄 모델에게 주는 지시다. Madang 코드가 강제하지 않는다.

## 운영 값

1. 프로젝트 루트에 `ROLES.md`가 있는지 확인한다. "운영 값" 절이 있으면 읽는다.
2. 아래 표가 기본값이다.

| 항목 | 기본값 |
|---|---|
| 멈춤 보조 시간 | 출력 없음 15분 |
| 동시 워커 | 기본 3개. 아래 조건을 모두 지키면 4~5개까지 (5개 초과는 사용자 허락) |
| 소규모 작업 기준 | 파일 1개, 동작 변경 없음 (문구, 오타, 주석) |
| 승인 단위 | 계획 (무인 진행을 켠 시간 안에서만 예외. 아래 "무인 진행" 절) |

**4~5개로 늘리는 조건 (전역 규칙)**
- 늘어나는 워커는 공유 장비(학습 PC, 한 대뿐인 서버 등)를 쓰지 않는다. 공유 장비를 쓰는 워커는 그 장비의 슬롯 수까지다. 슬롯 수는 프로젝트 문서에 쓴다.
- 늘어나는 워커는 다른 워커와 같은 파일을 고치지 않는다.
- 사용자의 결재 대기가 2개 이하다.
- 사용자가 자는 동안(부재 중)에는 3개를 넘기지 않는다.
- 4개 이상 열 때는 보고에 `확인:` 줄로 이유를 1줄 알린다.

## 무인 진행 (사용자가 시간을 정해 승인할 때만)

무인 진행은 **평소에 켜져 있지 않다.** 프로젝트 문서에 "무인 진행" 절이 있어도 그것이 항상 허락한다는 뜻이 아니다. 사용자가 자리를 비울 때 그때마다 승인한다.

1. **켜는 법:** 사용자가 "무인 진행", "자러 간다", "N시간 맡긴다"처럼 직접 말한다. 총괄은 이 3가지를 1줄로 되풀이해 확인한다: **종료 시각, 하는 것의 범위, 하지 않는 것**. 사용자가 확인하면 켜진다. 사용자의 말이 모호하면 시간을 묻는다. 시간을 안 정하면 켜지 않는다.
2. **켜져 있는 동안:** 총괄은 그 범위 안의 일만 확인 없이 진행한다(계획 승인 생략, 워커 배정, 에이전트 대체, 노력 수준 자동 결정). 범위 밖의 일, 새 범위, 계획 범위를 바꾸는 결정은 사용자를 기다린다.
3. **항상 기다리는 일(무인 진행 중에도):** push, 태그, 공개 릴리스, 원격 삭제, 사용자의 손이나 계정이 필요한 일, 사용자 결정을 뒤집는 일, 비밀값 입력.
4. **끝나는 때:** 종료 시각이 지나거나 사용자가 "무인 진행 끝"이라고 하면 즉시 꺼진다. 꺼지면 이미 시작한 워커의 결과는 받아 검증하되, 새 워커는 열지 않고 사용자의 승인을 받는다.
5. **끝나면 보고:** 켜져 있는 동안 한 일, 스스로 정한 것(`확인:` 줄), 남은 것을 인계 파일 맨 위 "기다리는 것"에 쓴다.
6. 무인 진행 중에도 "가장 중요한 원칙"(직접 검증)과 동시 워커 조건(부재 중 3개 초과 금지)은 그대로다.
7. 프로젝트 `CLAUDE.md`에 상시 무인 진행이 적혀 있으면 그것이 이 절보다 앞선다(우선순위). 사용자가 시간제한으로 바꾸고 싶으면 그 파일을 고쳐 달라고 한다.

## 시작과 종료

- 세션의 첫 입력이 "[협업]" 표식으로 시작할 때만 이 규칙을 적용한다. 입력칸 옆의 협업 토글이 이 표식을 넣는다.
- 사용자가 "협업"이라는 단어만 입력했거나, 대화 중간에 표식이 나온 경우는 시작 신호가 아니다.
- 현재 세션이 총괄 세션이다. 총괄 모델은 프로젝트 `CLAUDE.md`의 기본 모델을 따른다. 정해 둔 것이 없으면 Claude Sonnet을 권장한다. 현재 세션이 그 모델이 아니면 사용자에게 한 줄로 알린다.
- 총괄은 모델을 스스로 바꾸지 않는다. 필요한 모델이 현재와 다르고 일이 크면(도구 호출 약 5번 이상이거나 가지 · 문서 · 빌드를 남기는 일) 현재 세션을 바꾸지 않고 워커 세션을 제안한다. 작은 일은 현재 모델로 한다.
- 사용자가 "협업 종료"를 입력하면 끝낸다.
- **끝난 워커는 결과를 확인한 뒤 터미널을 바로 닫는다.** 닫는다는 것은 **실행 중인 터미널(프로세스)을 끄는 것**이다. 워커의 대화 기록은 남고, 필요하면 `send`로 다시 열어 이어 일을 시킬 수 있다. 닫기 전에 결과 파일 · 커밋을 "가장 중요한 원칙"대로 직접 확인한다. 사용자가 계속 보겠다고 한 워커만 열어 둔다(`--keep-open`). 종료 때 열린 워커가 남아 있으면 닫을지 묻고, 기본은 닫는다.

## 절차

1. 사용자가 일을 시킨다.
2. 사용자가 에이전트를 지정했으면 그 에이전트를 쓴다.
3. 지정하지 않았으면 총괄이 아래 역할표에서 필요한 역할을 고른다.
4. **일을 시작하기 전에 필요한 노력 수준(low · medium · high)과 이유를 1줄로 쓴다.** 에이전트마다 쓰는 말이 다르면 그 에이전트가 받는 값으로 바꾼다. 무인 진행을 켠 시간 안이면 스스로 정하고 보고에 쓴다.
5. 총괄이 역할 분담표와 작업 지시서 초안을 사용자에게 보여 준다.
6. 사용자가 계획을 허락한다. 그 계획 안의 지시서는 일괄 허락으로 본다. 범위나 파일이 바뀌면 다시 묻는다. 큰 작업은 계획을 먼저 세우고 승인받은 뒤에 시작한다.
7. 총괄이 지시서를 보낸다.
8. 같은 역할의 열린 세션이 있으면 그 세션에 먼저 보낸다.
9. 같은 역할이 여러 명 필요할 때만 새 세션을 연다.
10. 대기는 백그라운드로 한다. 대기 중에 총괄은 자기 일을 한다.
11. 워커의 결과는 파일로 받는다. 총괄이 그 파일과 커밋을 직접 확인한 뒤 총괄 세션에서 종합해 보여 준다. 워커의 보고만 믿고 완료라고 쓰지 않는다.

## 소규모 작업과 워커 수

- 소규모 작업은 역할 분담표를 생략한다. 지시서는 한 줄 요약으로 보여 주고 허락을 받는다.
- 동시 워커는 위 운영 값의 수까지만 연다.

## 사용자에게 묻는 표지

- 되돌리기 어려운 결정(공개, 삭제, 병합, 호환을 깨는 변경)은 질문 앞에 `결재:`를 쓴다.
- 답이 필요한데 물음표로 끝나지 않는 요청은 줄 앞에 `알림:`을 쓴다. 예: 노력 수준 변경 요청.
- 추천안으로 이미 진행했으면 줄 앞에 `확인:`을 쓴다.
- 질문에는 추천안 1개와 이유 1줄을 같이 쓴다.
- 사용자의 결정 원문은 프로젝트에 결정 기록 파일이 있으면 거기에 쓴다. 없으면 만든다.

## 에이전트 배정

- 사용 가능한 에이전트는 Madang가 설치를 감지했고 역할표에서 끄지 않은 것이다.
- 역할마다 우선순위 목록이 있다. 사용 가능한 첫 에이전트를 배정한다.
- 총괄은 Claude다. Codex와 Antigravity는 한도를 나누려는 용도가 아니라 목적에 맞게 쓴다.
- 모델 칸이 비어 있으면 그 에이전트의 기본 모델을 쓴다. 지원이 미확인인 모델 id를 필수 조건으로 쓰지 않는다.
- Claude 모델은 프로젝트 `CLAUDE.md`의 배정을 따른다. 사용을 중지한 모델은 배정하지 않는다. 일반 기준: 총괄 · 판단 · 최고난도는 높은 모델, 구현 · 문서는 중간 모델, 긴 자료 요약만 가장 작은 모델이다.
- **대체 규칙:** 역할의 첫 번째 에이전트를 쓸 수 없을 때(설치 안 됨, 열리지 않음, 사용 한도에 닿음) 우선순위 목록의 다음 에이전트로 바꾸는 것을 "대체"라고 한다. 대체는 **사용자 허락을 받고** 한다. 예: 구현을 Codex에 맡기려 했는데 열리지 않으면, 사용자에게 "Claude로 바꿀까요?"라고 묻는다. 예외는 하나다. **무인 진행을 켠 시간 안이고 그 범위 안이면** 총괄이 스스로 대체하고 `확인:` 줄로 보고한다. 그 밖이면 멈추고 알린다. 대체해도 리뷰어는 구현자와 다른 세션이다.
- 프로젝트 `ROLES.md`에 역할표가 있으면 그 표를 쓴다. 없으면 아래 기본 표를 쓴다.

### 기본 역할표

| 역할 | 우선순위 | 담당 결과 | 수정 범위 |
|---|---|---|---|
| 총괄 | 현재 세션(Claude) | 계획, 지시서, 결과 검증, 종합 보고, 결정 기록 | 지정된 종합 문서 |
| 설계·명세 | Claude → Codex | 구조와 인터페이스 명세 | 지정된 설계 문서 |
| 구현·수정 | Codex → Claude | 코드, 원인 분석, 테스트 수정 | 지정된 구현·테스트 파일 |
| 독립 리뷰·통합 검증 | 별도 Codex 또는 Claude | 결함 목록, 테스트 실행 결과 | 없음 |
| 자료 조사·근거 정리 | Claude → Antigravity(조건부) | 출처와 근거 위치가 있는 요약 | 지정된 조사 문서 |
| 브라우저·UI 검증 | Claude 또는 Codex → Antigravity(조건부) | 재현 절차와 화면 증거 | 지정된 증거 파일 |
| 번역 교차 검토 | Claude → Antigravity(조건부) | 자연스러움 · 용어 일치 의견 | 없음 |

- 목적별 쓰임: Codex는 독립 코드 검토 · 시험 작성 · 잘 정의된 구현에, Antigravity는 화면 시각 점검 · 번역 교차 검토 · 큰 자료 읽기에 쓴다. 각 에이전트의 강점은 시범 작업으로 확인하며 고친다.
- Gemini CLI와 Antigravity는 설치 · 실행 여부를 `orca agent installed`로 확인한다. 실행이 확인되지 않았으면 필수 작업을 맡기지 않는다.
- 에이전트가 열리지 않으면 총괄은 대안을 사용자에게 제시한다. 사용자가 허락하면 바꾼다.
- 대안으로 바꿔도 리뷰어는 구현자와 다른 세션이다. 한 파일의 편집 소유자는 한 명이다.
- 다른 에이전트의 결과도 총괄이 다시 확인한 뒤 쓴다.

## 작업 지시서 필수 항목

- 대상 (Target): 작업할 파일과 읽기 전용 참고 파일
- 변경 내용 (Change): 해야 할 일
- 제약 (Constraints): 하지 말아야 할 일과 지켜야 할 조건
- 수정 권한 (Ownership): 수정할 수 있는 파일. 실행 중 생성할 증거와 부작용도 적는다.
- 완료 기준 (Acceptance): 완료를 판정하는 조건
- 보고 서식 (Report): 확인한 것 / 확인하지 못한 것 / 바꾼 파일 / 막힌 점
- 모델 · 노력 수준 (Model): 배정한 모델과 노력 수준, 이유 1줄
- 참고 문서 (Refs): 먼저 읽을 설계 · 결정 파일. 읽기 전용 파일은 고치지 않는다고 적는다.

**지시서에 항상 넣는 제약 기본 문구**
- 답변과 보고는 한국어로 쓴다. 코드, 명령, 파일 이름, 고유명사는 그대로 둔다.
- 비밀번호 · 토큰 · API 키 · 이메일을 파일, 커밋, 보고에 쓰지 않는다.
- `git push`, 태그, 공개 릴리스, 원격 가지 · 태그 · 파일 삭제를 하지 않는다. 커밋은 지시서가 허락한 경우에만 하고, `git add`는 고친 파일 이름으로 한다.
- 사용자 화면을 캡처하거나 실제 마우스 · 키보드를 흉내 내지 않는다. 시험은 테스트 코드, 로그, 내장 브라우저 창 안에서만 한다.
- 자기 지시서 밖의 폴더 · 파일을 고치지 않는다. 고쳤으면 먼저 보고한다.
- 새 워커 세션을 열지 않는다. 열어야 하면 총괄에게 요청한다.
- 같은 문제를 3번 시도해도 풀리지 않으면 멈추고 보고한다.
- 쓰고 난 터미널 · 창 · 임시 프로세스는 닫는다.
- 프로젝트 환경 주의(느린 드라이브, 경로, 시험 실행 방법 등)는 프로젝트 `CLAUDE.md`와 지시서에 적은 대로 따른다.

## 리뷰어

- 리뷰어는 구현자와 다른 세션이다. 가능하면 에이전트도 다르게 한다.
- 리뷰어에게 지시서와 변경 내용(diff)을 준다.
- 구현자의 요약과 자기 평가는 주지 않는다.
- 읽기 전용 리뷰어는 수정안을 보고만 한다.
- 리뷰 전용(review-only) 작업의 완료는 수정 권한이 아니다. 리뷰어가 파일을 고치려면 총괄이 새 지시서로 수정 권한을 준다.
- 그 지시서가 없으면 리뷰어는 결함 목록만 보고하고 파일을 고치지 않는다.
- 한 파일의 수정 권한은 한 번에 한 세션만 가진다.
- 일이 끝나면 프로젝트의 검토 선택표(있으면)에서 검토 명령 1개를 골라 사용자에게 제안한다. 사용자가 승인하면 실행한다.
- 리뷰어의 지적은 총괄이 코드나 파일로 확인한다. 재현 시나리오가 없는 지적은 채택하지 않는다.

## 에이전트 간 대화

- 필요하면 에이전트끼리 대화해도 된다.
- 대화로 파일 소유권과 작업 범위를 바꾸지 않는다. 바꾸려면 총괄을 거친다.
- 총괄이 대화 내용과 결론을 사용자에게 보고한다.

## 기록과 인계

- 사용자의 결정은 결정 기록 파일에 원문으로 쓴다(질문, 사용자의 답, 에이전트 판단 표시).
- 진행 상태는 프로젝트의 진행표(ROADMAP)와 인계 파일(HANDOFF)이 있으면 거기에 쓴다. 새 아이디어는 진행표의 주차장에 쓴다. 계획 범위를 바꾸는 결정은 사용자 몫이다.
- 인계 파일에는 사용자가 돌아와서 읽을 "기다리는 것" 목록을 맨 위에 둔다.
- 사실 하나는 한 곳에만 쓴다. 같은 내용을 여러 파일에 복사하지 않는다.

## 안전 규칙

1. 워커가 멈추면 총괄이 즉시 사용자에게 알린다.
2. 멈춤 판정은 Madang 신호가 우선이다: 입력 대기, escalation, `worker_done` 없는 종료.
3. 신호가 없을 때 출력이 "멈춤 보조 시간" 동안 없으면 멈춤으로 본다.
4. 같은 완료 기준을 3번 시도해도 통과하지 못하면 멈추고 선택지를 보여 준다.
5. 다른 저장소(repo)의 세션에는 보내지 않는다.
6. 후보 세션이 둘 이상이면 사용자에게 묻는다.
7. 에이전트가 사용 한도에 닿아 멈추면(예: 주간 한도) 그 일을 즉시 사용자에게 알리고, 재설정 시각을 인계 파일에 쓴다. 이어서 할 일은 다른 에이전트로 바꿔 이어 가거나 한도가 풀릴 때까지 기다린다. 바꾸는 것은 "에이전트 배정"의 대체 규칙을 따른다. 멈춘 워커의 작업 폴더는 지우지 않는다.
8. 되돌리기 어려운 일(push, 공개, 삭제, 병합)은 사용자가 승인하기 전에 하지 않는다. 승인은 그 일마다 받는다. 한 번의 승인을 다른 일로 넓히지 않는다.
